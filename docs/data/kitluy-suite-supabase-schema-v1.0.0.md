## 0. Scope, sources and precedence

This specification consolidates, without renaming, the relations defined by the canonical data dictionary and binds them to the business-rule corpus. It introduces **no** table or schema name that does not already exist in the primary source.

Primary source (schema and table names reused exactly):

- `docs/source/data-contracts/kitluy-suite-supabase-data-dictionary-v1.0.0.md` (cited below as **DD**, per-schema sections).

Cross-checked contracts:

- `kitluy-suite-supabase-enum-and-reference-data-registry-v1.0.0.md` (**ENUM**);
- `docs/source/business-rules/` — `kitluy-core-business-rules` (KBR-CORE-001..010), `kitluy-transaction-and-booking-lifecycle` (KBR-TXN-001..008), `kitluy-laundry-state-machines` (KBR-LND-001..008), `kitluy-payment-refund-and-void-rules` (KBR-PAY-001..009), `kitluy-inventory-movement-and-cost-rules` (KBR-INV-001..009), `kitluy-finance-subledger-and-reconciliation` (KBR-FIN-001..009), `kitluy-business-date-shift-and-close-rules` (KBR-SHIFT-001..008), `kitluy-pricing-discount-tax-and-rounding-rules` (KBR-PRC-001..008), `kitluy-customer-identity-consent-and-privacy` (KBR-CUS-001..008), `kitluy-configuration-publication-and-rollback` (KBR-CFG-001..009);
- `docs/source/qa/kitluy-payment-and-reconciliation-test-vectors-v1.0.0.json` (`money_contract`, 26 canonical vectors);
- `docs/source/security/` — RBAC permission registry (107 permission keys), audit event registry, sensitive-action and four-eyes policy (A0–A4), resource-scope model;
- `docs/source/offline/kitluy-storehub-local-database-schema-v1.0.0.md` (**HUB**, `edge_*` schemas) — mapping in §6, subject to open conflict KLREC-2026-07-26-002;
- Implemented consumers: `verticals/phase1-laundry` (booking lifecycle, production and T2 state machines, custody events, terminal profiles) and `packages/payments` / `packages/money` (tenders, KHQR, refunds, voids, cash session, settlement). The cloud schema must be able to represent every state and record these consumers emit.

Shared conventions (DD "Shared database conventions") are binding throughout: `uuid` primary keys (client-generated UUIDv7 for offline-created operational records where the approved toolchain supports it), `tenant_id uuid NOT NULL` on every tenant-owned row, explicit `digital_store_id` / `store_location_id` where applicable, `timestamptz` stored in UTC, integer minor-unit money (§4), `numeric(18,4)` quantities with integer grams for authoritative Laundry weight snapshots, no destructive deletion of finalized financial/custody/audit truth, JSON never replacing authoritative relational fields, scoped idempotency keys on every side-effecting RPC, plural `snake_case` relations, deterministic constraint/index names, and mandatory `COMMENT ON` metadata.

## 2. Per-domain entity contracts

Format: one compact contract row per DD relation — **not** DDL. Exact column-level DDL, index names and defaults belong to migrations; the observed dictionary generated from `pg_catalog` is compared against DD and this contract in CI. Column lists name only contract-critical columns; every tenant-owned relation additionally carries the §0 scope and timestamp conventions even where not repeated.

Abbreviations — _Scope_: T = `tenant_id uuid NOT NULL`, DS = `digital_store_id uuid`, SL = `store_location_id uuid`. _MC_ (mutation class): `MUT` = mutable lifecycle row (governed status transitions), `CFG-V` = mutable configuration with `version` optimistic concurrency (generic last-write-wins prohibited), `IMM-V` = immutable version/snapshot row (corrections publish a higher version), `A/O` = append-only ledger/evidence (UPDATE/DELETE rejected for normal application roles; corrections via compensating records), `DRV` = derived (system-maintained; never client-written).

## 3. Invariant enforcement matrix

Enforcement legend: **PK/FK/UNIQUE/CHECK/EXCL** = declarative constraints; **TRG** = database trigger; **RPC** = security-definer database function as the only write path; **RLS** = row-level security policy (specified in the companion RLS document); **APP** = application domain service (TypeScript packages/verticals); **HUB** = offline Store-Hub local contract (`edge_*` serializable procedures + sync protocol). Application-only validation is never claimed as a database constraint; where the database mechanism awaits migration authoring or a DD amendment, that is stated.

| #   | Invariant                                                                                                                                                                                                                              | Rule source                                                       | Enforcement mechanism(s)                                                                                                                                                                                                                                                                                              |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| I1  | Tenant/Digital-Store/Location scope isolation: every tenant-owned row carries `tenant_id NOT NULL`; cross-scope references are invalid                                                                                                 | KBR-CORE-001; DD conventions                                      | NOT NULL + FK (same-scope validation on high-risk paths, DD acceptance criterion 4) + RLS on every tenant-scoped relation + APP context resolver (`packages/tenant-context`, `digital-store-context`); RLS enforced regardless of UI                                                                                  |

## 5. Naming, keys and mutation classes (cross-cutting)

- **Naming:** schemas and tables plural `snake_case` in the cloud tier exactly as DD defines; functions verb-first `snake_case`; deterministic constraint/index names (migration-owned; exact migration-created names win in CI comparison).
- **Primary keys:** `uuid`. Offline-created operational records (Bookings, tenders, custody events) use client-generated UUIDv7 where the approved migration/toolchain supports it, otherwise UUID with immutable origin identity (DD conventions; KBR-TXN-004).
- **Scope columns:** `tenant_id` NOT NULL on tenant-owned rows; `digital_store_id`/`store_location_id` explicit where the domain requires them (per-entity rows in §2).
- **Timestamps:** `timestamptz` UTC; display default `Asia/Phnom_Penh`. `business_date` columns derive per KBR-SHIFT-001, never from raw client clocks.
- **Mutation classes:** every table carries a declared class (§2 `MC` column). All `A/O` relations reject UPDATE/DELETE for normal application roles (DD acceptance criterion 5). `CFG-V` relations require `version` optimistic concurrency; generic last-write-wins is prohibited for finance, inventory quantity, payment, custody and approval truth.
- **JSON:** metadata/provider snapshots/forward-compatible extension only. No authoritative money, inventory, permission or custody field exists only inside JSON (DD acceptance criterion 6).
- **Comments:** every schema/table/column/view/materialized view/function/policy uses `COMMENT ON` with owner, purpose, sensitivity class, append-only/mutable status and canonical document reference.
- **Status vocabularies:** native PostgreSQL enums only for small, truly stable technical sets; business lifecycle/status/reason codes live in `kitluy_core.reference_values` or domain reference tables with effective dates, translations and migration-owned transition matrices (ENUM registry). Reason-code rows carry category, severity, required note/evidence/approval flags and applicability.
- **Generated evidence:** the repository must generate `artifacts/db/observed-data-dictionary.{json,md}` and `artifacts/db/schema-diff.{json,md}` from `pg_catalog`, including migration hash, Git SHA and Supabase project/environment (DD generation rule and acceptance criterion 7).
