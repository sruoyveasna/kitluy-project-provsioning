## 1. Amendment rule (additive only)

1. This amendment is **strictly additive**. It adds **no schema** and appends ten relations to the existing DD `kitluy_core` relation-dictionary section. It renames, removes, re-types, re-scopes and supersedes **nothing** in DD v1.0.0. Every existing DD schema, table, column contract, constraint, invariant and ID remains untouched and in force exactly as published.
2. Every relation introduced here carries the marker: **"Amendment-002 additive; supersedes nothing; existing DD IDs untouched."**
3. Existing DD relations are **referenced, never duplicated**. In particular `kitluy_core.customers` and `kitluy_core.customer_contacts` remain the sole owners of customer-identity and contact-identifier truth (they are referenced by FK, not amended); `kitluy_notifications.preferences` remains the DD-owned preference projection; the `kitluy_storefront` identity relations (`customer_channel_identities`, `customer_phone_challenges`, `customer_sessions`) stay DD-owned Storefront relations.
4. Authority order is inherited unchanged from DD v1.0.0 ("Authority and implementation-truth rule"). Shared database conventions (uuid PKs with client-generated UUIDv7 for offline-created records, `tenant_id uuid NOT NULL` where tenant-scoped, `timestamptz` UTC, integer minor-unit money, plural `snake_case`, scoped idempotency, `COMMENT ON` metadata, JSON never replacing authoritative relational fields) apply to every relation below without restatement.
5. Companion documents (RLS pack, migration plan, enum/reference-data registry, RPC/trigger contract, seed plan) require their own governed follow-up amendments; this document declares the target contract they must satisfy but modifies none of them.

## 2. Pre-authoring check — existing customer/consent naming in DD v1.0.0

Checked first, as required. DD v1.0.0 already defines **`kitluy_core.customers`** ("Unified customer identity") and **`kitluy_core.customer_contacts`** ("Phone/email/contact points") in its `kitluy_core` relation dictionary — those two relations are **NOT amended** here; the ten relations below only reference them. DD's only other consent-adjacent storage is `kitluy_notifications.preferences` ("Consent/channel preferences", the derived preference projection), the `consent_status` column on `customer_contacts`, and the unrelated `kitluy_admin.support_access_sessions.consent_ref`. No DD relation stores consent purposes, purpose/notice versions, grant or withdrawal events, privacy requests/decisions, customer-store relationships, merge workflow records or customer status history.

Absence proof: a whole-document search of DD v1.0.0 for the ten table names `customer_store_relationships`, `customer_merge_requests`, `customer_merge_results`, `customer_status_history`, `consent_purposes`, `consent_purpose_versions`, `consent_grants`, `consent_withdrawals`, `privacy_requests`, `privacy_request_decisions` returns **zero occurrences** (grep over `docs/source/data-contracts/kitluy-suite-supabase-data-dictionary-v1.0.0.md`, 2026-07-27). This matches reconciliation record C2. All ten names follow the DD plural-`snake_case` convention and live in the existing `kitluy_core` schema (Shared Platform owns customer truth — reconciliation §1.4/§1.5).

## 3. Scope and boundary

This amendment defines the relational contracts required by cycle §9/§10 (KLD-2026-07-26-003) and [KBR-CUS-001, KBR-CUS-003, KBR-CUS-004 and KBR-CUS-006](../source/business-rules/kitluy-customer-identity-consent-and-privacy-v1.0.0.md): customer-to-Digital-Store relationships, the governed duplicate-merge workflow (request → append-only result, tombstone preservation, distinct requester/reviewer), append-only customer status history, the consent purpose registry with immutable notice versions, append-only consent grant/withdrawal events (consent is never a mutable boolean), and append-only privacy requests with their decisions.

**Boundary:** identity, consent and privacy-case truth only. The preference projection stays in `kitluy_notifications.preferences` (DD relation, never authoritative over the append-only consent records); channel identity, phone (OTP) challenges and public sessions stay in `kitluy_storefront` (DD relations); no relation here stores raw phone challenges, raw tokens or unmasked display defaults beyond the DD/KBR-CUS-005 data-minimization contracts. Nothing here decides privacy workflow depth, legal basis, retention, OTP values, merge approval thresholds or the purpose registry content — see §11 (explicit non-scope).

## 4. Schema ownership registry

**No new schema is added** — a deliberate difference from Amendment-001 (which added `kitluy_finance`). All ten relations live in the existing **`kitluy_core`** schema, whose DD schema-ownership registry row (Owner **Shared Platform**; responsibility "Tenant, Partner, Digital Store, Store Location, membership, customer, catalog and plan-neutral identity") already covers customer truth and remains **unchanged**. Consent and privacy-case records are Tenant-owned customer truth and therefore Shared Platform-owned (reconciliation §1.5); the table comments additionally note the operating sub-roles "Shared Platform (Consent and Privacy Service)" and "Shared Platform (Privacy Operations)" without creating a new schema owner.

Amendment-002 additive; supersedes nothing; existing DD IDs untouched.
