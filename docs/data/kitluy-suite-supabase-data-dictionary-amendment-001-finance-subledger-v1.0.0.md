## 1. Amendment rule (additive only)

1. This amendment is **strictly additive**. It adds one schema (`kitluy_finance`) to the DD schema ownership registry and one relation-dictionary section. It renames, removes, re-types, re-scopes and supersedes **nothing** in DD v1.0.0. Every existing DD schema, table, column contract, constraint, invariant and ID remains untouched and in force exactly as published.
2. Every relation introduced here carries the marker: **"Amendment-001 additive; supersedes nothing; existing DD IDs untouched."**
3. Existing DD relations are **referenced, never duplicated**. In particular the `kitluy_payments` schema (tenders, refunds, voids, provider events, settlement refs, payment reconciliations) stays the sole owner of payment, provider-event and payment-reconciliation truth; this amendment only adds foreign-key/linkage contracts toward it.
4. Authority order is inherited unchanged from DD v1.0.0 ("Authority and implementation-truth rule"). Shared database conventions (uuid PKs with client-generated UUIDv7 for offline-created records, `tenant_id uuid NOT NULL`, `timestamptz` UTC, integer minor-unit money, plural `snake_case`, scoped idempotency, `COMMENT ON` metadata, JSON never replacing authoritative relational fields) apply to every relation below without restatement.
5. Companion documents (RLS pack, migration plan, enum/reference-data registry, RPC/trigger contract, seed plan) require their own governed follow-up amendments; this document declares the target contract they must satisfy but modifies none of them.

## 2. Pre-authoring check — existing finance naming in DD v1.0.0

Checked first, as required: DD v1.0.0 enumerates 24 `kitluy_*` schemas in its schema ownership registry; **none** is a finance-subledger schema, and no relation in any existing schema provides journal, posting, account-dimension or source-posting-registry storage. The finance domain is currently distributed (schema specification §1 row 11) across `kitluy_payments` (settlement refs, payment reconciliations), `kitluy_partner` (expenses, reconciliation snapshots), `kitluy_pos` (shift/drawer truth) and `kitluy_billing` (SaaS invoices). The schema specification records this as an explicit gap ("Not enumerated in DD v1.0.0 … not invented here (ADR-0005)"). The schema name `kitluy_finance` is therefore new, follows the DD `kitluy_*` plural-`snake_case` convention, and matches the already-scaffolded application owner `@kitluy/finance` (`packages/finance`, KLMF-FIN-005=B).

## 3. Scope and boundary

This amendment defines the relational contracts required by [KBR-FIN-001, KBR-FIN-002 and KBR-FIN-004](../source/business-rules/kitluy-finance-subledger-and-reconciliation-v1.0.0.md): balanced double-entry journal storage, an operational account dimension, a source-to-subledger posting identity/idempotency registry, and finance command dedupe — with full tenant/Digital-Store/Location/actor/device context and business-date/shift binding ([KBR-SHIFT-001..008](../source/business-rules/kitluy-business-date-shift-and-close-rules-v1.0.0.md)), persisting the postings emitted by the tested engine in `packages/payments/src/ledger.ts` (with `refunds.ts` and `settlement.ts`).

**Boundary (KLMF-FIN-005 = B):** operational finance subledger only. KitLuy owns operational finance records, liabilities, reconciliation and accountant-ready exports; it is **not** a statutory ERP, general ledger, tax-filing or payroll system. Nothing here creates statutory account mappings, tax logic, rounding policy or accounting-policy values — see §10 (explicit non-scope).

## 7. Reconciliation runs/items linkage (reference, not duplication)

Reconciliation lifecycle relations already exist in DD v1.0.0 and are **not** re-created here: `kitluy_payments.payment_reconciliations` / `payment_reconciliation_lines` (KBR-FIN-005/007, KBR-PAY-009) and `kitluy_partner.reconciliations` / `reconciliation_lines` (KBR-FIN-005/006). This amendment adds the linkage contracts only:

1. **Run/item → journal:** an adjustment or fee posting produced by resolving a reconciliation exception is a `kitluy_finance.journal_entries` row with `source_type` = `PAYMENT_RECONCILIATION_LINE` (or the partner equivalent) and `source_id` = the difference row, registered exactly once in `source_postings`. Existing resolution reference fields on the reconciliation-line relations (`resolution_ref` / `resolution_movement`-style columns per DD) may cite the resulting `journal_entries.id`; their column contracts are unchanged.
2. **Journal → run:** reconciliation completion (KBR-FIN-005) reads journal truth; completion, reopen, completeness criteria and required sources stay governed by the existing relations and by owner values FIN-OD-002 (completeness during delayed Hub sync) and FIN-OD-003 (cash variance/blind-count policy) — not decided here.
3. **Provider-event uniqueness (reference):** provider callback replay safety remains owned by `kitluy_payments.payment_provider_events` with its existing UNIQUE `(provider_key, provider_event_id)` contract (schema specification §3-I9). Finance relations reference tenders/refunds/settlement refs derived from verified provider events; they never re-ingest provider callbacks and add no second provider-event store.

## 9. Invariants (enforcement designation)

Designation legend follows the schema specification §3: CHECK/UNIQUE/FK = declarative constraint; TRG = trigger (constraint trigger where cross-row); RPC = security-definer function as the only write path; RLS = row-level security. Application-only validation is never claimed as a database constraint.

| #      | Invariant                                                                                                                                                                                                                             | Designation                                                                                                                                                                                                                                                                                      |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| AMD-I1 | **Balancing (KBR-FIN-002):** per journal entry and per currency, sum of DEBIT legs = sum of CREDIT legs; at least two legs; zero-value legs prohibited; one currency per entry absent an approved FX bridge                           | Cross-row aggregate — a plain column CHECK cannot express it: deferrable **constraint TRIGGER** validating each posted entry at transaction commit + posting **RPC** as the primary gate + **CHECK** `amount_minor > 0` and direction/currency CHECKs on legs. | AMD-I2 | **Append-only enforcement (KBR-FIN-001; governing principle 4):** posted journal entries, postings and POSTED source registrations are never updated or deleted; corrections are linked compensating entries                          | **RLS**: UPDATE and DELETE **PROHIBITED** for all application roles (PC-AO class per the [RLS pack](kitluy-suite-supabase-rls-and-authorization-v1.0.0.md)) + `enforce_append_only` **TRG** rejecting UPDATE/DELETE + INSERT only via **RPC**                                                    |
| AMD-I3 | **Idempotency uniqueness (KBR-FIN-004):** exactly one journal per authoritative source effect per posting rule; scoped idempotency keys unique; replay returns the original result; changed source hash is a CONFLICT, never a repost | **UNIQUE** `(tenant_id, source_type, source_id, posting_rule_key)` + **UNIQUE** scoped idempotency keys on `source_postings`/`idempotency_records` + **RPC** request-hash comparison                                                                                                             |

| AMD-I6 | **No silent FX:** every leg and aggregate carries its currency; cross-currency entries are rejected; the USD/KHR mixed-tender and exchange policy remains an open owner value                                                         | **CHECK/NOT NULL** currency + AMD-I1 single-currency validation + engine parity (`CURRENCY_MISMATCH_OR_CONVERSION_REQUIRED`); policy stays `[REQUIRED]` PRC-OD-005 — no DB mechanism may presume it                                                                                              |
