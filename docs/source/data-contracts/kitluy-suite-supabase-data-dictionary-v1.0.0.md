> **Mission:** Define the ownership, relational shape, type contract, foreign-key direction, constraint expectations and invariants for every target Supabase relation in the current KitLuy Phase 1 foundation, while preserving SQL migrations as the only deployed schema truth.

## Authority and implementation-truth rule

This artifact is a **canonical target implementation contract**. It is not evidence that a database object, policy, function, seed, deployment, backup, or test exists.

Authority order:

1. Current KitLuy project-owner decisions and the active KitLuy Project Instructions.
2. Applied SQL migrations, verified repository code/tests, deployed environment evidence, and production evidence.
3. `kitluy-suite-supabase-schema-v1.0.0.md`, `kitluy-suite-supabase-rls-and-authorization-v1.0.0.md`, and `kitluy-suite-supabase-migration-plan-v1.0.0.md`.
4. This artifact and the other documents in the Supabase implementation pack.
5. Current Suite, Business, product, Store Hub, infrastructure, and API specifications.
6. Approved handoffs and evidence-based comparison/classification documents.
7. Competitor clone documents and superseded planning.

**Applied SQL migrations are the final deployed schema truth.** Documentation may generate, review, explain, or validate migrations, but it must never become a parallel database definition. A documentation-to-migration mismatch must fail CI or be recorded in the reconciliation register before release.

No capability may be labeled `IMPLEMENTED` without repository, applied-migration, executable-test, deployment, and applicable pilot/production evidence.

## Shared database conventions

| Area                   | Canonical rule                                                                                                                                                                                             |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Primary keys           | `uuid`; offline-created operational records use client-generated UUIDv7 where the approved migration/toolchain supports it, otherwise UUID with immutable origin identity.                                 |
| Tenant scope           | Every tenant-owned row carries `tenant_id uuid NOT NULL`; Digital Store and Location scope are explicit where applicable.                                                                                  |
| Digital Store          | `digital_store_id uuid`; the business/control-plane entity with exactly one primary vertical.                                                                                                              |
| Store Location         | `store_location_id uuid`; optional physical edge site under a Digital Store.                                                                                                                               |
| Timestamps             | `timestamptz`, stored in UTC; default display timezone `Asia/Phnom_Penh`.                                                                                                                                  |
| Money                  | Integer minor units: KHR in riel (`bigint`, exponent 0), USD in cents (`bigint`, exponent 2), with `currency_code char(3)` where mixed-currency records are possible. Never use floats.                    |
| Quantities             | `numeric(18,4)` for measured quantities; integer grams may be used for authoritative Laundry weight snapshots where required by the pricing contract.                                                      |
| Soft deletion          | Only for mutable catalog/configuration records where permitted. Finalized finance, payment, inventory movement, audit, event, and custody records are never destructively deleted.                         |
| JSON                   | Optional metadata, provider payload snapshots, or forward-compatible extensions only. JSON must not replace authoritative relational fields.                                                               |
| Idempotency            | Every side-effecting API/RPC accepts a scoped idempotency key and stores request hash plus result reference.                                                                                               |
| Optimistic concurrency | Mutable configuration aggregates use `version bigint` or immutable version rows; generic last-write-wins is prohibited for finance, inventory quantity, payment, custody, and approval truth.              |
| Audit                  | Sensitive actions include actor, effective role/permission, resource scope, environment, device/service identity, reason, request/correlation ID, and immutable before/after references or payload hashes. |
| Localization           | Codes remain language-neutral; display labels live in translation/reference tables, not enum literals.                                                                                                     |
| Naming                 | Schemas and tables are plural `snake_case`; functions are verb-first `snake_case`; constraints/indexes use deterministic names.                                                                            |

## Dictionary generation rule

This file contains the approved logical dictionary baseline. The repository must also generate an **observed dictionary** from migrations or the target database using `pg_catalog`, including columns, types, defaults, nullability, PKs, FKs, checks, unique constraints, indexes, RLS state, policies, functions and comments. CI compares the observed dictionary with this contract. Exact migration-created names win; unresolved differences fail validation.

Required generated artifacts:

- `artifacts/db/observed-data-dictionary.json`
- `artifacts/db/observed-data-dictionary.md`
- `artifacts/db/schema-diff.json`
- `artifacts/db/schema-diff.md`

## Reporting/read-model dictionary

`kitluy_reporting` contains migration-defined views/materialized views only. Required Phase 1 read models include:

| View/read model                       | Minimum contract                                                                                               |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `chain_overview_read`                 | Chain scope, included/excluded Location counts, source version, `as_of`, freshness, completeness.              |
| `chain_location_summary_read`         | Digital Store/Location identity, health, operations, finance-safe aggregates, source and reconciliation state. |
| `chain_location_comparison_read`      | Standardized metric definition version, currency, period, included Locations and exclusions.                   |
| `chain_laundry_operations_read`       | Booking pipeline, production status, Ready count, pickup aging, exception counts.                              |
| `partner_dashboard_read`              | Role-safe Partner summary with source, `as_of`, freshness and completeness.                                    |
| `partner_finance_summary_read`        | Reconciled/read-only finance summary; never a mutable ledger.                                                  |
| `pos_booking_context_read`            | Store Hub/terminal-safe intake context, prices/version, customer and outstanding balance.                      |
| `storefront_public_status_read`       | Public-safe availability, queue state and freshness; no private operational fields.                            |
| `fleet_health_read`                   | Device/Hub status with last heartbeat, software version, certificate and rollout state.                        |
| `authorization_effective_grants_read` | Computed effective grants for diagnostics only; authorization still enforced by API/RLS/helpers.               |

Every read model must declare source relations, metric definitions, refresh behavior, staleness thresholds, security barrier/RLS strategy, and whether it is transactional, normal view, materialized view or asynchronously built projection.

## Required database comments

Every schema, table, column, view, materialized view, function and policy must use `COMMENT ON` with: owner, purpose, sensitivity class, append-only/mutable status, and canonical document reference. The generated dictionary includes these comments.

## Dictionary acceptance criteria

1. Every migration-created relation appears in the observed dictionary.
2. Every target relation in this document is either present, feature-flagged with an approved future migration, or recorded in the reconciliation register.
3. Every table has an owner, PK or explicit key contract, scope columns, sensitivity classification and mutation class.
4. Every FK is indexed on high-use paths and validates same-Tenant/Digital Store/Location invariants where required.
5. All append-only tables reject UPDATE/DELETE for normal application roles.
6. No authoritative money, inventory, permission or custody field exists only inside JSON.
7. The migration hash, Git SHA and Supabase project/environment are included in generated evidence.
