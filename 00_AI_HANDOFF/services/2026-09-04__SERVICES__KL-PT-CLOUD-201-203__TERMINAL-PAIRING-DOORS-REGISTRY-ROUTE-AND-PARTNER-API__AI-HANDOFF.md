## 1. Outcome

- **The cloud now has a physical terminal.** `kitluy_devices.physical_terminals` is a named seat in a Store with an ordered role set (`physical_terminal_roles`, soft-removed) and an append-only event log. The name is optional and generated as `Terminal N` when blank; unique per Store case-insensitively; roles are validated structurally and must belong to the Store's own vertical (no vertical vocabulary in Fleet).
- **One code for one seat.** `terminal_pairing_sessions` mirrors the Store Hub session model: 8-character Crockford code, digest only, fifteen minutes, five attempts, single use, one open session per seat (opening another supersedes it). A session opens only against an ACTIVE Store Hub at the seat's Location and snapshots the live roles.
- **The Pi learns everything from the code.** `evaluate_terminal_pairing_session_v1` resolves by code alone and returns the owner's §7 context from server rows (tenant, Store, Location, Store Hub, seat, roles, vertical, environment; `required_app_family` and `release_channel` honestly null until the application-family model exists). `consume_terminal_pairing_session_v1` performs the whole assignment through the 0121 doors — claim, redeem (`enrolled → awaiting_trust`), one terminal assignment per role — then marks the session consumed and binds the seat, all in one transaction.
- **Only an Admin-approved device pairs**, and there is now one definition of eligible: migration 0214 makes `evaluate_provisioning_eligibility_v1` accept Admin approval evidence for the current enrollment in development and pilot (production still needs factory QA). The real terminal `KL-6783D70CB6BF` went from "no factory QA execution is recorded" to eligible with no reasons on `kitluy-fresh`.
- **Two least-privilege identities**: `kitluy_terminal_issuance_service` (Partner side: define, set roles, open, cancel, alphabet) and `kitluy_terminal_pairing_service` (device side: evaluate, consume). Neither holds table access; no browser role reaches any door; the new tables are under forced RLS with no policies.
- **Device registry**: `POST /v1/terminal-pairing` (`deviceRecordId`, `code`) — the same shape and refusal discipline as Hub pairing, then the same separate trust advance; the response carries the §7 `context`.
- **Management API**: Partner routes to list a Store's seats, define one, set its roles, open a session (code shown once, no QR), watch it and cancel it, behind the new permission `fleet.terminal_pairing_code.issue` (CRITICAL, granted to `DIGITAL_STORE_STAFF`) and a separate Store-scope check. `/partner/stores` now carries each Store's vertical and Store Hub readiness (`active` / `pending_trust` / `none`). `GET /devices/{id}` reads readiness from the database predicate and adds an `assignmentContext` in words. Every route is declared in `openapi.yaml`, including four that were missing before.
- **Migrations 0213 and 0214 are applied on both local stacks** (`kitluy-fresh`, the hardware stack; `kitluy-repo17`, the canonical test stack, which was also caught up from 0203 to 0212). Ledger rows were recorded by hand because the repository's `db:apply` wrapper refused on a diverged CLI migration history.

## 5. Implementation details

### Schema/data/migrations

0213: `physical_terminals`, `physical_terminal_roles`, `terminal_pairing_sessions`, `physical_terminal_events`; doors `define_physical_terminal_v1`, `set_physical_terminal_roles_v1`, `open_terminal_pairing_session_v1`, `evaluate_terminal_pairing_session_v1`, `consume_terminal_pairing_session_v1`, `cancel_terminal_pairing_session_v1`; helpers `physical_terminal_live_roles_v1`, `validate_physical_terminal_roles_v1`, `active_store_hub_at_scope_v1`, `record_physical_terminal_event_v1`. Refusal codes `KLUY-PHYSTERM-*` and `KLUY-TERMSESSION-*` returned as jsonb; 0121 refusals raise and abort consumption. 0214: `create or replace` of the predicate, same signature and grants. Forward-only; no destructive statements (`create or replace trigger`).

### APIs/events/jobs/webhooks

Registry `POST /v1/terminal-pairing` → 200 `{deviceRecordId, sessionId, assignmentId, assignmentGeneration, storeAssignment, context{…}, activated, lifecycleState, trustedTime, activationRefusal, certificate, detail}`; refusals `SCOPE_PERMISSION_DENIED` (wrong/locked code), `RESOURCE_VERSION_CONFLICT` (race, already assigned), `VALIDATION_FAILED` (request problems), 503 when unwired. Management API routes as listed in the README; the 201 issuance body is `{code, sessionId, expiresAt, ttlSeconds: 900, showOnce: true, physicalTerminalId, label, terminalProfileKeys, storeHubReference, environment, detail}`.

### Permissions/audit/security

New permission `fleet.terminal_pairing_code.issue`; `fleet.device_provisioning_code.issue` stays HET-only. Two NOLOGIN identities with exactly their doors (the 0213 guard counts granted capabilities and names each door). Every seat/session change is an append-only event with the actor. The code exists only in the API process and the HTTP response; the database holds a digest. Tenant never accepted from a request. Not-yours is 404; missing permission and out-of-scope are one 403.

### Offline/Store Hub/device impact

The Hub is a precondition (active projection) and is re-checked at presentation and consumption. The Pi side is unchanged in this slice: no shell types a code yet.
