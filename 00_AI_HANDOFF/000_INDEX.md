## A Pi Terminal is served by its Store Hub (2026-09-11)

Record: [`edge-platform/38_A_TERMINAL_IS_SERVED_BY_ITS_STORE_HUB.md`](edge-platform/38_A_TERMINAL_IS_SERVED_BY_ITS_STORE_HUB.md)
· **PROVEN ON HARDWARE, END TO END** · `SERVING` · every bootstrap route 200 · not committed · no hosted write · Hub image rebuilt, Terminal image unchanged

From a clean slate — cloud fleet truncated, both boards on new cards — a Pi Terminal now discovers its Hub over mDNS, completes mutual TLS, pairs with mutual proof, and reads authority time, eligibility and configuration, all 200. The owner chose an Ed25519 pairing credential over relaxing the signature bound, and it proved the cheap option: the terminal was already signing with its device identity key and the cloud already held that key's fingerprint, so the work was entirely Hub-side and the Terminal image needed no change. **Five defects, each real:** (1) DER serial padding in the projection producer — the cloud stores `008fc0…`, the certificate says `8fc0…`, which breaks on roughly HALF of all serials at random and is why this passed on 09-10 and failed on 09-11; (2) the Hub held no `device_credential` of its own, so it served, recognised the terminal and then refused every pairing; (3) migration 0042 — the pairing transcript bound the RSA transport credential when both sides sign with Ed25519 identity keys, making the handshake unsatisfiable from either end (the 120-char bound was left untouched; Ed25519 is 86); (4) the Hub signer declared the TLS certificate's serial while signing with a different key; and (5) **pre-existing and the most serious** — `pairing_session_proof_state_ck` asserted an equality that made a session which verified a proof and then expired impossible to sweep, and the governance trigger blocks fixing it by hand, so that terminal could never pair with that Hub again. 176 agent tests green; both changed tests were updated to assert the new behaviour, not relaxed.


## A Pi Terminal dials its Store Hub, and the exact wall it stops at (2026-09-10)

Record: [`edge-platform/37_A_TERMINAL_DIALS_ITS_STORE_HUB.md`](edge-platform/37_A_TERMINAL_DIALS_ITS_STORE_HUB.md)
· **PROVEN ON HARDWARE, PARTIAL BY DESIGN** · terminal recognised, Hub authority time serving · not committed · no hosted write · **both images need a rebuild**

The Pi Terminal image shipped no edge client at all, and the Hub's local identity projection was entirely empty — `terminal_device`, `hub_device` and `hub_assignment` all zero rows — because the cloud producer that delivers them is BLK-006 and nothing in the Hub sync layer performs network I/O. Built: a root `kitluy-terminal-edge.service` in the firstboot-agent (mDNS discovery, mutual TLS, discovery verification, Hub-local pairing, bootstrap reads, a status file the sandboxed Device Shell can read), plus `hub-provision-terminal` — a development stand-in for the producer, refused outside `development` and refused for any Store but its own, fed by `pnpm hub:terminal-projection`, which copies facts the cloud already holds and invents none. Two findings cost real time and are now asserted against: the desktop app's `lan-client.ts` uses Node's DEFAULT server-identity check, which **cannot** pass against a KitLuy device certificate (URI-only SANs, no DNS/IP name), so the new client binds the DEVICE and pins the fingerprint the signed record names; and the Hub matches the **X.509** serial observed in the handshake, not the KitLuy `DEV-...` label, so a projection carrying the label matches nothing while looking correct. Proven on the boards: mDNS → mTLS → signed record → recognised → **`authority-time` ok**. **Owner ruled a development-only signer is permitted, and it is built:** `publishDevelopmentConfiguration` records, verifies and activates a snapshot through the REAL pipeline (never writing `state='active'` behind the verifier), using the sanctioned `DevelopmentHmacBatchSigner` with a key generated on the Hub at 0600 that never leaves it, refusing `production`, `pilot` and `unknown` alike before it opens a database connection; the LAN `deliverySigner` is wired only when the image declares `development`. That moved the Hub from `PAIR_PROFILE_FORBIDDEN` to a pairing session that opens. **A second wall then appeared, and it is a real cross-component mismatch:** the Hub verifies the pairing proof against the credential it holds, that credential is **RSA-2048** (`OPERATIONAL_KEY_TYPE = "rsa"`, and the cloud certificate agrees), and the pairing route caps a signature at 120 base64url chars — ed25519 is 86 and fits, RSA-2048 is 342 and does not. `crypto.verify(null, …)` accepts RSA fine, measured; the caps are the obstacle. Widening a signature bound on a security route was not done on my own judgement. Owner decision, recommended order: an Ed25519 pairing credential beside the RSA transport one, an Ed25519 operational key, or wider caps. 536 agent tests, 720 image gates, all green.


## The Store Hub serves terminals, and the three image defects that stopped it (2026-09-10)

Record: [`edge-platform/36_THE_STORE_HUB_SERVES_TERMINALS.md`](edge-platform/36_THE_STORE_HUB_SERVES_TERMINALS.md)
· **PROVEN ON HARDWARE** · Store Hub serving mTLS on `:7443` · fixed in the image sources · not committed · no hosted write · **running board carries runtime drop-ins that die on reboot**

The Hub was not serving at all, and three independent defects in `infra/kitluy-store-hub-image` each explained it. (1) `/run/postgresql` was never created: postgresql-common's tmpfiles rule never runs on a read-only erofs root (`systemd-tmpfiles-setup` is condition-skipped), and the provision script's `install -d -m 2775` fallback is blocked by the unit's own `RestrictSUIDSGID=yes` because 2775 carries the **setgid** bit — the ENOENT you see is the chown step complaining about a directory the blocked mkdir never made. Bisected with three replica units on the board. Fixed with `RuntimeDirectory=postgresql` + `RuntimeDirectoryMode=2775` + `Preserve=yes` + `Group=postgres`, so PID 1 applies the setgid mode before the sandbox exists; verified under the real sandbox before the source was edited. (2) `RestrictAddressFamilies` omitted `AF_NETLINK`, so libuv died with `uv_interface_addresses returned Unknown system error 97`. (3) The DSN connected as `postgres` while the unit runs as `root` under peer auth — a previous session diagnosed exactly this, created the `root` role, and never corrected the DSN. All three surfaced as one misleading `KLUY-HUB-DB-UNREACHABLE`, because `isHubDatabaseReachable()` swallows every error into a bare `false`. Hub now advertises `_kitluy-edge._tcp` and refuses a client with no certificate; the Terminal already holds its adopted certificate. **The remaining gap is that nothing on the Pi Terminal image talks to the Hub** — the edge client lives in `apps/kitluy-pos-desktop-app` and is not packaged into the image. 322 image gates green.

## The Hub reached ACTIVE, and a device class was wearing a trust level's clothes (2026-09-01)

Record: [`edge-platform/2026-09-01__EDGE-PLATFORM__BRINGUP-002__STORE-HUB-REACHES-ACTIVE-ON-HARDWARE__AI-HANDOFF.md`](edge-platform/2026-09-01__EDGE-PLATFORM__BRINGUP-002__STORE-HUB-REACHES-ACTIVE-ON-HARDWARE__AI-HANDOFF.md)

**A physical Pi 5 went from a wiped card to `active` with two portal clicks and a
typed code.** `manufactured -> enrolled` 01:35:07, `-> awaiting_trust` 01:36:30,
`-> active` 01:36:36 — six seconds, unassisted. BRINGUP-001's blocker is closed.

**The certificate blocker was one word in the wrong vocabulary.**
`hardwareTrustLevel: readImageEnv("KITLUY_DEVICE_CLASS")` sent `store_hub`, but
that enum admits only `development_software | tpm_2_0 | secure_element`. The
column went NULL — and `concat_ws` SILENTLY DROPS NULL arguments, so the database
built 16 canonical TBS fields where `tbsBytes()` built 17. The bytes could never
match. 0127's comment claims it "mirrors tbsBytes() field for field": true for
non-NULL input, quietly false otherwise, and **any nullable field in that list can
reproduce it**.

**It took hours because nothing would say what diverged.** The refusal said only
"the two layers disagree"; the route logged nothing at all; and the device could
not report the code either, because the client reads top-level `code`/`details`
while `errorEnvelope` nests them under `error` — so every refusal arrived as a
generic `OPCERT_REFUSED`. The precise code existed on both sides of the wire and
was visible on neither. Making the divergence name its field — `field 20 of 23
(local 9 chars, database 20)` — found the bug in seconds.

**Activation was asked once, too early, and never again.** It needs a certificate,
but `advanceDeviceTrust` runs during pairing, and a Hub only requests a
certificate AFTER it pairs. So pairing's attempt was correctly `blocked` and
nothing reconsidered it: a Hub with every precondition satisfied sat at
`awaiting_trust` for ever. The certificate route now re-checks trust the moment
the last precondition becomes true.

**Board continuity is confirmed:** one board, two SD cards, cloud registration →
ONE device row at installation generation 2. Open enrollment had produced seven
rows for the same board.

**Left open, and worse than it looks:** `kitluy-enrollment-agent` crash-loops on
hardware — the binary is absent from the `store-hub` profile and `Restart=always`
