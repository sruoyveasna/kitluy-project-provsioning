## 1. Mission read-back, and what was actually missing

The owner mission asked to "complete the integration of the KitLuy POS application and its required backend/store-operation functionality" so that a provisioned Pi Terminal performs Store operations under its **device identity**, never an email/password. Inspection found that architecture already built and proven on hardware (handoffs 36–52): device certificate + mTLS, pairing, the Store Hub as local authority, the Terminal PIN as the only human credential (actor = the terminal), the T1 face, and the real catalog delivered through the signed configuration (slice 1). The one thing a device could NOT do was the Store operation itself: **no Booking, no lines, no payment, no receipt** could be written on the Hub from the terminal — the T002 draft was the end of the road, and the Hub's WS-09 command library (`confirmIntake`, `recordCashPayment`, `queueReceiptPrint`) existed as a tested library with no route, keyed to a staff actor the Pi does not have.

**Root causes of "store operations cannot execute", as found**

| #   | Cause                                                                                                                                                                                                                                                                                                                       | Where                                  |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| 1   | The canonical command pipeline's authorization (`authorizeHubCommand`) required an `edge_identity.staff_cache` row for the actor; a Terminal PIN session's actor is the terminal device, which has none — so every WS-09 command was unreachable from a Pi                                                                  | `hub/authorization.ts`                 |
| 2   | The generation check compared the terminal's presented generation with the **Hub's** own `hub_assignment.assignment_generation` (Hub 5 vs terminals 1/4 on the development Store) — every command would refuse `EDGE_ASSIGNMENT_GENERATION_MISMATCH` on the real Hub (KLREC-2026-09-19-ASSIGNMENT-GENERATION-SEMANTICS-001) | same                                   |
| 3   | No LAN route served confirm-intake, no quote, no Bookings read; the edge bridge's closed list did not forward any                                                                                                                                                                                                           | `hub/edge/routes.ts`, `edge-bridge.ts` |
| 4   | Commands need a terminal-issued `kl1.{terminal}.{sequence}` key with a Hub-verified client sequence; the terminal held no sequence and no way to learn it                                                                                                                                                                   | offline contract §2/§4                 |
| 5   | The Hub had no parser for the delivered `catalog`/`money` sections (only the terminal had one) and no pricing over them                                                                                                                                                                                                     | —                                      |
| 6   | The Booking Draft could not name the Booking it became                                                                                                                                                                                                                                                                      | Hub 0040                               |
| 7   | The face's Pricing/Review steps were honest stubs ("WS-12-T004/T005")                                                                                                                                                                                                                                                       | face                                   |

Nothing about the email/password model had to be "adapted": the standalone POS's Supabase auth never reached this repository (T1-FACE-PORT-001 rejected it), and the Pi path's boundary test (`pi-terminal-boundaries.test.ts`) still refuses `password|email|sessions/open` in Pi-path code. The device credential + Terminal PIN **is** the credential for this slice, exactly as KLD-2026-09-17 ruled.
