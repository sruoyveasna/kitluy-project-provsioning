## 1. Outcome

The Pi Terminal image tree now builds the same way the Store Hub tree does, and Factory Enrollment (KLD-2026-09-03-FACTORY-ENROLLMENT-001) is the terminal's first and only identity stage:

- `runtime-manifest.json` is the one declaration of what the terminal image contains; the packaging script refuses on any disagreement with the overlay, and the tests read it.
- The flash-time ticket enrollment agent, which landed a device in `enrolled` with no Admin decision, is retired: its unit, enable symlink, shim and packaged modules are gone and asserted absent by every suite.
- Cloud registration (self-registration → `manufactured` / "waiting for approval" → explicit Admin approval → `enrolled`) is packaged, enabled and ordered after firstboot; the tty1 text screen shows the registration state and the owner's own sentence for an approved-but-unassigned terminal.
- The image carries no Store authority of any kind, and that absence is asserted (no Hub agent, no database, no Hub migrations, no avahi edge advert, no business application).
- The builder states the environment, bakes the device class, the registration route and the hardware profile key, and refuses the stale `store-hub` profile in this tree.
- Four terminal suites plus the agent suite pass at source level, and the built rootfs passes the image-contents inspection (68 checks) and the secret scan (17 checks). Getting there took four builds: three died inside `apt-get update` because the agent's SANDBOXED shell cannot reach `deb.debian.org` (the owner's own terminal fetched it normally, and an unsandboxed call did too); the owner's own run then died in the appliance-clock hook because nothing declared `tzdata` (the Hub inherits it from PostgreSQL). Build 4, unsandboxed and with `tzdata` declared, produced `build/work/deploy-v2.7.0/kitluy-pos-terminal-wayland-arm64.img.zst` (sha256 `6f1c937ca3bcf14bb96014e5fba2ea2b6c6db7808a850b436281d2a3deeb9bb9`, classification DEVELOPMENT / UNSIGNED / NOT BOOT-TESTED). Nothing has been flashed; that is the owner's next step (§13).
- **Proven on a Raspberry Pi 5 the same evening** (board `pi5-byqwcr`, `172.16.30.241`, build-4 card): the text screen showed the device id and \"Waiting for approval\"; the cloud recorded `KL-6783D70CB6BF` class `terminal` under `KL-PI5-TERMINAL-DEV` in `manufactured`; approval through `pnpm dev:device:approve` (operator `OP-VEASNA`, the Admin Portal was not running locally) moved it to `enrolled`; within one poll the board logged `phase=APPROVED` and the screen read \"Approved / Store: Unassigned\" with the owner's Phase A sentence; after a reboot the first journal line of the new boot was already `phase=APPROVED`, the screen unchanged, and the cloud still held exactly one terminal record. No Store authority on the board: `/usr/lib/kitluy` holds only the bootstrap set, only SSH listens on the LAN (CUPS and the resolver stub bind loopback; LLMNR 5355 is open, see §9), no `pairing-state.json`.
- **Two blockers found and fixed on the way, neither in the image**: the stack's edge-function runtime container had been dead for 25 h and its function directory pointed at a cleaned scratchpad (every board logged `REGISTRATION_500` then `BOOT_ERROR`; restored, see §7), and the appliance-clock hook needed `tzdata`.
- **Screen defects seen on the board, fixed at source**: it showed the opaque cloud id instead of the `KL-` name the Admin Portal lists, and \"Image version ..... Unknown\". The screen now derives the asset tag from the registration key exactly as the client does (one helper, `assetTagFromFingerprint`) and reads `KITLUY_IMAGE_VERSION` from `image.env`. In the next card, not on the flashed one.

Two agent-level defects were fixed on the way: the health reporter hard-coded `deviceClass: "terminal"` (a lie on every Store Hub) and reported `degraded` for ever on any device without the retired agent's state file.

## 5. Implementation details

### Functional behavior

Boot: `kitluy-firstboot` (identity) → `kitluy-cloud-registration` (loop: register, wait for Admin approval, poll every 60 s) → `kitluy-bootstrap-screen` on tty1 (5 s refresh) with `kitluy-health-reporter`, `kitluy-update-agent` and `kitluy-ssh-hostkeys` alongside. `kitluy-terminal-session` (labwc) stays defined and disabled as the manifest's declared tty1 successor; `kitluy-terminal-client` stays defined, disabled and executable-less (governed release).

### Schema/data/migrations

`NONE`. No migration authored or applied to any environment.

### APIs/events/jobs/webhooks

`NONE` new. The terminal calls the existing cloud registration route (`KITLUY_REGISTRATION_URL`, Supabase Edge Function `device-registration`) with the baked `KITLUY_HARDWARE_PROFILE_KEY`.

### Permissions/audit/security

No authority is granted by the image. `scan-image-secrets.sh`, `secret:scan`, `pki:assert-no-dev` pass. The image ships no per-device state, no secret, no assignment truth, no Store-authority artefact (asserted at source and on the built rootfs). Environment is stated by the builder and asserted by the layer; `pilot`/`production` are refused.

### Offline/Store Hub/device impact

Terminal only. The Store Hub tree is unchanged; its three source-level suites were re-run and pass (build-gates 32/0, systemd-runtime 150/0, environment-gating 19/0). The Hub overlay's committed copies of `health-reporter.js` are the previous build's; the next Hub build refreshes them through its own packaging step and picks up the device-class fix.

### UI/localization/accessibility

Text screen on tty1 (English, as before). Rows: Device id, KitLuy (Waiting for approval / Approved / …), Store: Unassigned, Network, Image version, Agent version, headline. For an approved device: "This Terminal has not yet been assigned to a Store." and "Pairing is not available in this build; Store assignment arrives with a later release." No input, no path to any application.

### Observability/runbooks/docs

`infra/kitluy-os-image/README.md` rewritten. Health beat now carries `class=<from image.env> registration=<phase>`.
