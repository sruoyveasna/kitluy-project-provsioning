**Date** 2026-09-19 · **Area** edge-platform · **Status** IMPLEMENTED · TESTED · HARDWARE VERIFIED on the development Store Hub (hot-deployed; Hub image NOT yet rebuilt) · DEVELOPMENT ONLY · **Commits** `7813fa3`, `ed0e87d` on `dev` (worktree `0bef5a7`, `0bbc6ac`).

## 1. What was asked

Owner, 2026-09-19, after the third by-hand Hub provisioning of the week: "Do we have any way that we can make this run automatically? I am not able to ask you to do it every time like this." Then "Do A: connect first, then implement the automatic", and "now start implement it".

Until this morning a newly paired Pi Terminal reached its Store Hub only after a person ran `hub-terminal-projection.mjs` on a workstation, carried the JSON to the Hub, ran `hub-provision-terminal --delivery`, and published the development configuration — once per terminal, every time; on 2026-09-18 the step that closes the previous grants was forgotten and produced `PROFILE_NOT_T1` against a correct-looking Hub (handoff 50 §7).

### Second proof, from a purge (2026-09-21)

The owner reflashed the offline terminal `KL-1CB3577C26A7` and asked for it to be gone from the development cloud so the card would register as a brand-new Pi. Reason it was needed: the board had already been reflashed four times and kept the SAME record each time — registration recognises the hardware by `soc_serial` / `mac_address` (`hardware_manifest_signals`), so a reflash alone never produces a new device.

Purged with `scratchpad/purge-devices.sql` (`mode=plan` first, `keep_seats=''` — the owner chose to remove the seat as well): **214 rows across 31 tables**, all hanging off that one device, plus its seat `Pi HEllo` with 7 role grants and 16 events. Afterwards: no device with that tag, no signal carrying its MAC or SoC serial, no orphan release installation; the other two terminals keep their assignment, certificate, enrollment and release rows.

Two operational notes worth keeping:

- **`postgres` is not enough.** The first execute refused with `permission denied for table device_credentials` and rolled the whole transaction back (nothing deleted) — in a Supabase stack `postgres` is not a superuser and is not a member of `kitluy_credential_issuer`, which owns `device_credentials` and `device_credential_heads`. Re-run as `supabase_admin` inside the database container (its own `POSTGRES_PASSWORD`, never printed) and it commits. The refusal is the ownership model working, not a broken script.
- **The Hub retired the terminal by itself in under 60 s**: `terminal-sync.json` went `v7 → v8` and the terminal left the list without anyone touching the Hub. Both running terminals stayed `SERVING` with their PIN state `set` across the configuration bump. This is HUB-TERMINAL-SYNC-001 proven a second time, now on removal rather than addition.

### Why the Hub could not simply be updated, and what changed (2026-09-22)

Auditing the live Hub for reboot safety found the hot-deploy exactly as expected — `/var/lib/kitluy/hotfix-4b9c069/main.mjs` and its trust record are on the persistent partition and survive, but the systemd drop-in that points the unit at them is under `/run` and does not. **A Store Hub reboot therefore reverts to the baked agent, which carries no terminal-sync at all** (`grep -c` for its markers in `/usr/lib/kitluy/lib/hub-agent/main.mjs`: **0**), and terminal auto-provisioning stops with no error anywhere. The Hub had been up 5 days, so nothing had exposed it.

The obvious answer — ship a governed release, as the Terminals take — was closed: the Hub's own update agent had been waking every five minutes saying *"no public release trust anchor in /etc/kitluy/trust; refusing to consider any payload"*, and that directory did not exist. The image has shipped `kitluy-update-agent.service` and its code since it existed; the **builder never baked an anchor or a release source**. So every Hub change cost a reflash — and a Hub reflash rewrites the card, wiping `/persistent`, the Store's own database.

Fixed in `c2fc0d5`: the Hub builder gains `--release-source` and bakes the PUBLIC development release-signing record; the Hub layer writes `/etc/kitluy/trust/release-signing.json` and `/etc/kitluy/release.env`; and `image-contents` §5c refuses an image that ships the update agent without an anchor — a unit that can never act is a reflash waiting to happen.
