## 5. Core invariants

All races must preserve these invariants:

- one authoritative terminal state per code;
- one direct successor per predecessor;
- at most one outstanding ISSUED code per assignment;
- no replacement from REVOKED, LOCKED or REDEEMED predecessor;
- predecessor never returns to ISSUED;
- replacement lineage is immutable;
- failed-attempt count never exceeds five;
- no terminal-state timestamp conflicts;
- no duplicate terminal event;
- no duplicate replacement CREATED event;
- raw code returned only by the transaction that creates the successor;
- raw code never persisted;
- active-Hub rule enforced at the replacement commit boundary;
- no uncontrolled unique/check/FK exception escapes as the public contract;
- no role, permission, test-clock or borrowed-membership residue.

## 6. Required race A — replacement versus revocation

Initial state:

- one assignment;
- one active Hub;
- one overdue ISSUED provisioning code;
- no successor.

Race:

- A: issue replacement using a new idempotency key;
- B: revoke the overdue predecessor.

Use separate PostgreSQL sessions with recorded backend PIDs and a synchronized
barrier.

Allowed final outcomes depend on serialization.

### Replacement wins first

Required:

- predecessor becomes EXPIRED;
- exactly one successor becomes ISSUED;
- revocation receives a stable terminal classification;
- predecessor remains EXPIRED;
- successor remains ISSUED;
- one EXPIRED event;
- one successor CREATED event;
- no REVOKED event on the expired predecessor.

### Revocation wins first

Required:

- predecessor becomes REVOKED;
- replacement issuance does not create a successor;
- no EXPIRED event;
- no successor CREATED event;
- one REVOKED event;
- replacement returns a stable terminal result.

Never allow:

- predecessor both EXPIRED and REVOKED;
- successor created from a REVOKED predecessor;
- duplicate terminal events;
- orphan lineage;
- uncontrolled constraint error.

## 7. Required race B — replacement versus fifth failure

Initial state:

- one overdue ISSUED code;
- failed-attempt count = 4;
- active assignment and Hub;
- no successor.

Race:

- A: issue replacement;
- B: present one incorrect code through the 0164 evaluator.

Because expiry is authoritative and checked before digest/attempt mutation,
the expected governed result is:

- predecessor EXPIRED;
- failed-attempt count remains 4;
- no LOCKED event;
- one EXPIRED event;
- exactly one successor ISSUED;
- one successor CREATED event;
- the failed presentation receives the stable expired classification.

If repository execution proves a different serializable order is permitted,
document the exact authority before accepting it.

Never allow:

- predecessor both EXPIRED and LOCKED;
- failed attempts above five;
- successor created from a LOCKED predecessor;
- duplicate events.

## 8. Required race C — replacement versus correct presentation

Initial state:

- one overdue ISSUED code;
- active assignment and Hub;
- no successor.

Race:

- A: issue replacement;
- B: present the predecessor’s correct code.

Required:

- predecessor finishes EXPIRED;
- correct presentation does not produce durable MATCH_READY after expiration;
- no redemption occurs;
- one successor ISSUED;
- exactly one EXPIRED event;
- exactly one successor CREATED event;
- no failed-attempt increment;
- no PRESENTED event after the expiry transition.

A transient MATCH_READY returned before the replacement transaction commits
must remain non-authoritative and must be documented as requiring P02B3’s
mandatory state recheck.

## 9. Required race D — replacement versus Hub deactivation

First inspect the actual Hub activation and deactivation authority.

activation projection directly.

- Hub currently active;
- assignment currently bound to that Hub;
- no successor.

Race:

- A: replacement issuance;
- B: governed Hub deactivation, revocation, replacement or other canonical
  transition that makes the Hub ineligible.

Required final behavior:

### Replacement commits while Hub is still authoritatively active

- successor may be created;
- successor binds to the Hub state valid at commit;
- later Hub deactivation does not rewrite historical issuance evidence;
- follow-on terminal provisioning must still revalidate Hub eligibility where

- no successor;
- predecessor may remain overdue ISSUED or become EXPIRED only according to
