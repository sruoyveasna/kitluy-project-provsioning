## 8. Decision rationale

Verdict: **PASS-WITH-CONDITIONS**. The engine is faithful to the acceptance contract and fails closed everywhere money could be invented; the one HIGH finding breaks retry semantics, not money conservation.

1. **Money integrity — verified.** Every amount path flows through `@kitluy/money` bigint minor units; number inputs are gated by `Number.isSafeInteger` (floats rejected with zero ledger effect — reviewer-probed on cash, refund, callback and settlement paths). The engine contains no rounding operation at all, so KHR is trivially EXACT_INTEGER and USD HALF_EVEN is never triggered (no decimal op exists — the strict reading of "only where a decimal op requires it"). Currency mismatch throws the canonical code in both directions (USD-on-KHR and KHR-on-USD) before the idempotency store or record stream is touched, so PAY-VEC-004's `no_ledger_effect` is structural, not incidental.
2. **Append-only — bypass hunt negative** (within the package's typed surface). The only ingress is `append()`; every record is deep-frozen including postings, posting Money objects and meta; frozen-mutation attempts throw; no update/delete API exists on the prototype; `getRecords()` copies; every aggregate (paid, refunded, net, balance, deposit, drawer net, state) is derived from the record stream on read. Corrections are compensating records; the full-refund case retains the original PAYMENT record byte-identical. Residual exposure is the in-process `@internal` surface (RV-005) — real, but out of the package's threat model.
3. **KHQR truth — verified.** `applyKhqrClientConfirm` appends only a non-financial `CLIENT_CONFIRM_OBSERVED` record with `authoritative: false`; there is no code path from any client/UI input to a PAYMENT record. Unverified events are quarantined with zero effect. Dedup by provider txn id survives duplicate and out-of-order delivery with exactly one business effect (PAY-VEC-009/011/012 + reviewer probes: SUCCEEDED→FAILED→SUCCEEDED keeps one effect). Amount mismatch appends a RECONCILIATION_EXCEPTION with the exact variance (−1000 on PAY-VEC-010) and never partially applies. The one nuance is RV-002: conflicting-status redelivery is silently treated as duplicate (fails closed — a masked success, never a false payment).
4. **Idempotency — one real defect.** Same key + same payload replays the original result for cash and attempts; same key + different payload (including a different command type, since the fingerprint carries a `type` discriminator) hard-conflicts with the canonical error code. The fingerprint is `stableStringify` over the internally normalized payload (sorted keys recursively, bigint-tagged); the theoretical bigint/string collision (RV-004) is unreachable through the engine's own command construction. **But refunds validate refundable balance before the idempotency lookup (RV-001)**: a full-refund replay with the identical key+payload throws and appends a false `REFUND_REJECTED` audit record instead of replaying. Reviewer-reproduced. This violates the canonical idempotency convention the task's own header cites and is exactly the offline/retry scenario the engine exists to make safe. It fails closed (no double refund), which is why the verdict is PASS-WITH-CONDITIONS rather than FAIL — but it is blocking for merge-equivalent acceptance of payment logic.
5. **Refund/void — verified** (aside from RV-001's replay path). Refundable = net paid including prior refunds: after a partial refund the ceiling shrinks correspondingly; exceeding it rejects with the canonical code and no new financial effect (the rejection audit record carries no postings, and the harness asserts `financialEffectCount` unchanged). Approval evidence is mandatory. Void of a finalized payment is refused unconditionally — the `approvalId` input cannot flip `allowed`, which is hardcoded `false` at the type level — and redirected to the compensating workflow.
6. **Writer's recorded ambiguities — checked against the contracts.** No numbered ambiguity file exists in-repo (same gap as WS-07; the markers live in code comments). Each recorded assumption was verified as genuinely unspecified rather than an invented rule where the contract decides: **(a) deposit_minor derivation** (`ledger.ts` `depositMinor`: a payment counts as deposit when the booking is still unpaid after applying it) — no contract text defines the formula; KBR-PAY-004 only forbids conflating deposit with settlement; the vectors pin exactly two data points (PAY-VEC-002, PAY-VEC-013) and the derivation matches both without contradicting any rule. Genuinely unspecified — correctly an interpolation, and it should be listed in the G1 ambiguity register. **(b) 24h settlement SLA default** (`settlement.ts` `DEFAULT_SETTLEMENT_SLA_HOURS = 24` with a `[REQUIRED: owner-approved settlement SLA]` marker) — reviewer searched the vectors JSON, KBR-PAY-009 and the finance subledger doc: no SLA is specified anywhere; PAY-VEC-024 (age 72h flagged) passes for any SLA < 72. The `[REQUIRED]` marker is honest and the default is conservative. Verified truly unspecified. **(c) refund approval mandatory** — strictest reading; all three refund vectors carry `approval_id`; threshold policy correctly deferred to PAY-OD-002. **(d) KHQR amount-match baseline** (attempt amount, else outstanding balance) — KBR-PAY-003 says "match amount" against the intent but vectors 009–011 carry no attempt; matching against outstanding balance reproduces PAY-VEC-010's expected variance exactly. Reasonable strict reading. **(e) compressed KHQR SUCCEEDED vector shape** = attempt + verified callback, and **(f) `signatureVerified: true` assumed for vector callbacks** — the vectors carry no signature field and PAY-VEC-008 is titled "signed success callback"; the unverified path is separately covered in engine.test.ts. **(g) booking-ledger `reconciled` hard-false** — this one IS contract-decided (KBR-PAY-009/KBR-FIN-007: the Hub can never claim settlement completion) and the code follows the contract. None of the recorded assumptions invents a rule the contract actually decides.
7. **Harness honesty — verified**, not assumed: unknown expected keys throw, empty expectation sets fail, all 26 IDs individually execute (verbose-reporter extraction), and the meta-test pins the vector count. The `display_rounding_not_applied_to_truth` assertion is a proxy (stored total and paid equal the exact input integer) — acceptable given the engine has no rounding path at all.
